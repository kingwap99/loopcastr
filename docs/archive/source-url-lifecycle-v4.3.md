## 0. 先更正一件事：<TARGET_HOST> 的角色

舊版把目標機當成「本機」，並在 `--observe` 的描述裡混用 `127.0.0.1:9997`，這是錯的。實際關係是：

| 位址 | 角色 | 現況【實測】 |
|---|---|---|
| **<TARGET_HOST>** | **獨立的播出主機**，未來要裝在這裡跑 | macOS 27.0／arm64／`hw.model=<MODEL>`（M1 13 吋）／帳號 `<USER>`。<br>**yt-dlp、ffmpeg、streamlink、MediaMTX 全部未安裝**，只有 `/usr/bin/python3` |

| 兩台對外 | **共用同一個公網 IP `<PUBLIC_IP>`**（同 NAT） | 這一條直接決定來源 URL 的壽命，見 §1.1 |

SSH 已通：`ssh <USER>@<TARGET_HOST>`。本輪所有量測都在工作機的 MediaMTX 上跑；目標機只做了連通性與 URL 可達性測試（§5.2）。

## 1. 第 1 項：來源 URL 生命週期管理

### 1.1 為什麼非做不可

【實測】用 `yt-dlp -g` 取出真實 YT 直播 manifest URL，觀察到三個硬事實：

1. **有到期時間**：路徑形式 `/expire/1789519713/`，值 = 解析當下 + **21600 秒（6 小時）**。
2. **綁解析當下的公網 IP**：URL 內含 `ip/<PUBLIC_IP>`，就是解析那一刻的公網 IP。
3. **URL 是長字串**：整條 1100 字元，無法人工拼湊，只能重新解析。

這代表舊架構「開播前解析一次、之後一路沿用」在 24/7 頻道上必然崩：6 小時後整批 URL 同時失效；PPPoE 重撥換 IP 也會整批失效。

（**【推論】** 到期後 googlevideo 會拒收 segment 請求——這是已知行為，但本輪沒有等 6 小時實測，故標為推論。）

### 1.2 【實測】解析與判斷邏輯（程式實作驗證）

`work/playout/relay.py` 新增 `url_expiry()` / `url_freshness()` / `RESOLVED_AT`，逐項驗證：

| 測項 | 輸入 | 結果 |
|---|---|---|
| path 形式 expire | `.../expire/1789518722/...` | 正確解出 `1789518722` |
| query 形式 expire | `...?expire=1900000000&foo=1` | 正確解出 `1900000000` |
| 無 expire 欄位 | `https://h/x.m3u8` | 回 `None`（不強制換手） |
| 真實直播 URL 剩餘 TTL | 解析後立即檢查 | **20782 秒 ≈ 5.77 小時** |
| 已解析 1799s（門檻 1800） | 沿用舊 URL | 判定**可用** |
| 已解析 1801s（門檻 1800） | 重新解析 | 判定**失效** → 印出「來源 URL 失效（已解析 1801s 前），重解析」 |
| expire 剩 400s（餘裕 300） | 沿用舊 URL | 判定**可用** |
| expire 剩 299s（餘裕 300） | 重新解析 | 判定**失效** → 印出「來源 URL 失效（expire 只剩 299s），重解析」 |
| expire 剩 120s | 重新解析 | 判定**失效** → 重新解析 |
| `--url-max-age 0` | 不限年齡 | 判定**可用**（關閉此機制） |

四個邊界（1799／1801、400／299）都剛好切在正確那一側。

### 1.3 【實測】生產管線連續跑 304 秒：排定換手 6 次、接收端 0 斷點

指令：

```
python3 relay.py --playlist playlist-ytlive.json \
  --target rtmp://127.0.0.1:1935/live/ytlive \
  --observe --url-max-age 45 --watchdog 10 --only y1
```

（來源是 Lofi Girl 24/7 直播 `rFZHOHl-L8A`；`--url-max-age 45` 是為了在幾分鐘內逼出換手，不是建議值。）

| 觀測項 | 數值 |
|---|---|
| 總時長 | 304.045 秒 |
| 排定換手次數 | **6**（`refreshes=6`） |
| 故障重試次數 | **0**（`restarts=0`） |
| 換手時的 Manifest 解析 | 6 次全成功，各耗 2.26–2.65 秒 |
| 實際換手間隔 | 47.4–47.7 秒 ＝ **45 秒（URL 年齡）+ 約 2.5 秒（重新解析）** |
| 接收端離線總計 | **3.711 秒**，且**全部發生在開播前** |
| 6 次換手期間的接收端離線 | **0.000 秒** |
| Observer 取樣 | 5403 筆，`api_fail=0` |

換手能做到零斷點，是因為 `_restart(planned=True)` 的順序是「**先解析新 URL → 新 publisher 接手 → 才收掉舊的**」，而解析那 2.5 秒裡舊串流還在正常播出。

### 1.4 【實測】啟動時的一個浪費（順手抓到的）

每次啟動會對同一條 URL **解析兩次**：

```
[02:37:51.029] resolve y1 OK client=web_embedded (2.48s)  <- 排程前置
[02:37:51.995] resolve y1 OK client=web_embedded (1.94s)  <- URL 更新
```

原因：`prepare_job()` 在背景執行緒解析（耗時約 2.4 秒），但主執行緒的 `start_at` 只領先 1.5 秒，`_launch()` 等不到結果就自己再解析一次。**每次啟動白白多花約 2 秒、多打一次 YouTube。**

【建議】讓 `_launch()` 等 `prepare_job` 的解析結果（Event 或 Future），逾時才自己解析。改動很小。

### 1.5 建議參數

| 參數 | 建議值 | 理由 |
|---|---|---|
| `--url-max-age` | **1800**（30 分） | manifest TTL 6 小時，在 1/12 壽命就主動換掉；換手零斷點，多換無害 |
| `--url-expiry-margin` | **600** | 到期前 10 分鐘就換，留有重試空間 |
| `refreshes` 與 `restarts` 分開計數 | 已實作 | 一天 48 次排定換手若共用 `max_restarts` 額度，真正故障就沒重試機會了 |

## 2. 第 2 項：看門狗門檻——真實 YT 直播源壓測

### 2.1 來源的物理底線【實測】

直接讀 manifest：

| 欄位 | 值 |
|---|---|
| `#EXT-X-TARGETDURATION` | **5** |
| 片段長度 | 全部 `#EXTINF:5.0`，共 2880 段 |
| 播放清單型態 | `playlist_type/DVR`、無 `#EXT-X-ENDLIST` |
| 選到的格式 | `itag 95`（1280x720 / 30fps） |
| `#EXT-X-MEDIA-SEQUENCE` | 每 5 秒 +1（實測連續三次：471600 → 471601 → 471602） |

**結論：這條來源的資料是每 5.0～5.1 秒才來一批。任何短於 5.1 秒的「輸出停滯」門檻，都註定每個片段週期誤觸發一次。**

### 2.2 【實測】生產管線：門檻 3.0 秒 → 每 20 秒誤觸發一次

指令同上，只把門檻改成 `--watchdog 3`（＝程式預設值）：

```
[02:36:33.462] WARN  y1     輸出停滯 3.2s（門檻 3.0s）
[02:36:33.462] INFO  y1     切墊片 assets/transition.mp4（takeover）
[02:36:49.140] INFO  start y1     live   (restart #1)
[02:36:49.644] INFO  y1     來源恢復，切回直播
[02:36:52.982] WARN  y1     輸出停滯 3.0s（門檻 3.0s）
[02:37:13.044] WARN  y1     輸出停滯 3.2s（門檻 3.0s）
```

| 觀測項 | 數值 |
|---|---|
| 47 秒內誤觸發 | **3 次**（間隔約 19.5／20.1 秒） |
| 每次誤觸發的墊片停留 | **16.023 秒**（02:36:52.983 → 02:37:09.006） |
| 47 秒內已消耗的 `restarts` | **3 ／ 6** |

也就是說，**預設的 `--watchdog 3.0` 在真實 YT 直播源上是壞的**：每 20 秒把正常訊號當故障、切一次墊片。

### 2.3 【實測】門檻 6 秒與 10 秒 → 零誤觸發

| 輪次 | 門檻 | 時長 | 看門狗誤觸發 | 備註 |
|---|---|---|---|---|
| A | 3.0s | 47s | **3 次** | 見 §2.2 |
| B | 6.0s | **301.6s** | **0 次** | `restarts=1`，是 ffmpeg `-t 300` 到期正常結束（rc=0），非看門狗造成 |
| C | 10.0s | **304.0s** | **0 次** | 同時跑了 6 次 URL 換手，`restarts=0` |

### 2.4 【實測】合成壓測：`out_time_us` 平坦區間的分佈

另一路用 `work/playout/yt_live_stress.py` 對同一直播源取 180 秒基線（37 個平坦區間）：

| 統計量 | 值 |
|---|---|
| 平坦區間數 | 37 |
| p50 | **5.083 秒** |
| p95 | **5.100 秒** |
| 最大 | **5.105 秒** |

各門檻在 180 秒基線內的誤觸發次數：

| 門檻 | 2s | 3s | 4s | 5s | **6s** | 7s | 8s | 10s | 12s |
|---|---|---|---|---|---|---|---|---|---|
| 誤觸發次數 | 35 | 35 | 35 | 26 | **0** | 0 | 0 | 0 | 0 |

三條路徑（生產管線 3s／生產管線 6s、10s／合成壓測）互相印證，結論一致。

### 2.5 誤觸發的連鎖代價（這是真正的危險）

門檻調太低不只是「多切幾次墊片」，還有兩個複合傷害：

1. **吃光重試額度**。程式碼是 `if self.restarts >= self.args.max_restarts: return`——`max_restarts=6` 一旦被誤觸發耗光，**看門狗之後完全不再作用**，來源真的掛掉時頻道會停在凍結畫面上沒人處理。以實測速率（1 次／20 秒）外推，約 2 分鐘就會走到這個狀態。
2. **畫質與時間軸抖動**。每次誤觸發都換一次 publisher，接收端要重新協商，並浪費 2.5 秒重新解析 URL。

### 2.6 門檻結論

| 用途 | 值 | 依據 |
|---|---|---|
| 絕對下限（不可低於） | **6 秒** | 180 秒基線誤觸發 0 次，且為 5.1 秒片段節奏 + 餘裕 |
| **建議值** | **10 秒** | 6 秒與 10 秒在 300 秒實測都 0 次；10 秒對片段抖動更寬容 |
| 代價 | 真斷源偵測延遲 10–15 秒 | 24/7 頻道配墊片可接受 |
| `--startup-grace` | **15 秒** | 首個 progress 出現前，需容納 YouTube 端建流 + 2 個片段週期 |

**舊結論「3 秒門檻」只在工作機自製的假直播源（2 秒片段）成立，不可外推到真實 YT 直播源。**

## 3. 更正 v4.2：`bytesReceived` 不能當「畫面在動」的判準

### 3.1 【實測】真實數據

MediaMTX `/v3/paths/list` 的 `bytesReceived` 在兩輪 300 秒實測中：

| 輪次 | 零成長總時長 | 佔比 | 零成長區間數 | 最長一次 | ≥5.0 秒的次數 |
|---|---|---|---|---|---|
| 門檻 10s 那輪（304.045s） | **299.288s** | **98.4%** | 66 | **5.111s** | 24 |
| 門檻 6s 那輪（301.613s） | **290.467s** | **96.3%** | 61 | **5.134s** | 29 |

`relay.py` 自己印出的說明也對上了：「資料零成長間隔 66 段，最長 5.111s（HLS 是整段拉整段送，來源正常時每隔一個片段長度本來就會空一段）」。

### 3.2 更正內容

| v4.2 的說法 | v4.3 更正 |
|---|---|
| 用 `bytesReceived` 零成長判斷「接收端畫面是否在動」 | **對 live HLS 不成立**。publisher 每收到一個片段才回報一次增量，所以正常運作時 98% 的時間都是零成長 |
| `--flow-threshold` 預設 5.0 秒 | **在真實 YT 直播源上，5 分鐘會產生 24 次假警報**，必須提高 |

### 3.3 正確用法

| 判準 | 可以回答 | 不能回答 | 建議門檻 |
|---|---|---|
| ffmpeg `out_time_us` 階梯 | 來源**有沒有在產出內容** | 網路有沒有斷 | **10 秒**（§2.6） |
| MediaMTX `bytesReceived` | publisher **行程是否還活著** | 畫面有沒有在動 | **≥ 2 倍片段長度**，YT 直播＝**12 秒** |
| HLS manifest 的 `MEDIA-SEQUENCE` 是否前進 | 來源端**是否還在推進** | 本機是否卡住 | 2 個片段週期＝**10 秒** |

## 4. 【實測】頻寬與內容成本（原本沒排，順手量到的）

這關係到目標機能不能同時跑多條聯播，所以直接量：

| 項目 | 數值 |
|---|---|
| manifest 原始大小 | **3,388,533 bytes（3.39 MB，含 2880 段完整 DVR 視窗）** |
| manifest 經 gzip | **46,288 bytes**（壓縮率 **73 倍**） |
| ffmpeg 30 秒內重載 playlist | **12 次**（約每 2.5 秒一次） |
| → playlist 重載的實際流量 | 約 **0.15 Mbps**（gzip 後） |
| 串流本體 | 3,407,872 bytes / 38.27 秒 ≈ **0.71 Mbps** |

兩點要注意：

- **必須確認 ffmpeg 有開 gzip**。若沒開，每 2.5 秒重抓 3.39 MB ＝ **單條 stream 就要 11 Mbps**，是致命等級的浪費。本輪實測 ffmpeg 8.1.2 走 gzip，結果是 0.15 Mbps。
- **0.71 Mbps 是 Lofi Girl 這種近乎靜態畫面的值**。偶像團體的動態 MV／演唱會直播，`itag 95` 會拉高到 2～3 Mbps。規劃目標機的併發數時請以動態內容的高值估算，不要用 0.71 當通則。

## 5. 其他【實測】與待辦

### 5.1 `-t` 與排程不一致，會產生假故障

【實測】門檻 6 秒那輪，ffmpeg 在 02:47:55.620 以 `rc=0` 結束，比排定的段結束時間（02:48:04）早了約 9 秒，被 `_health()` 判成「行程提前結束 rc=0」而觸發墊片與一次 `restart`。

【建議】live 段不要下 `-t`（段的結束交給排程接管），或把「在 `stop_at` 附近的 `rc=0`」視為正常結束。

### 5.2 跨機使用同一條 URL 可行，但脆弱

【實測】在工作機解析出的 manifest URL，直接從目標機抓取：兩邊都 `http_code=200`、`size_download` 相同（3,371,253 bytes）。因為兩台共用同一個公網 IP，`ip/<PUBLIC_IP>` 的綁定條件剛好滿足。

【建議】即便如此，**仍應在真正要發佈的那台機器上解析 URL**。理由：一旦 PPPoE 重撥、或某一台改走不同出口，URL 內的 `ip=` 就會對不上，而且這種失敗在「兩台同 NAT」的現況下測不出來。

### 5.3 合成壓測有一項數據不可用（誠實標註）

`yt_live_stress.py` 用自建 HTTP CONNECT 代理注入「上游凍結」，**本輪失敗**：注入 25 秒，卻量到 53.279 秒平坦，且凍結期間 `last_progress` 仍持續前進；另一輪又量到 25.001 秒。兩輪行為不一致，且同輪的 `proxy_bytes_forwarded`（18.9 MB / 230 秒 ≈ 0.657 Mbps）與 `bytes_zero_growth` 結果互相矛盾。

→ **該檔的「注入停滯」與 bytes 相關數字一律不採用**；本報告只採用它的基線 `out_time` 分佈（§2.4）。

【待辦】要量「真斷源 → 偵測延遲」，建議改用 `pfctl` 封鎖 `googlevideo.com` 網段，而不是代理凍結。

### 5.4 本機 ffmpeg 能力限制

【實測】工作機 ffmpeg 8.1.2 **沒有** `drawtext` / `subtitles` / `ass`（缺 libfreetype），只有 `overlay` / `drawbox`；編碼器有 `h264_videotoolbox` 與 `libx264`。之後若要做字幕、跑馬燈、台標，不能用 drawtext，得走 overlay 貼圖或換工具鏈。

### 5.5 【實測】目標機落地前的環境檢查（本輪補做）

| 項目 | 值 |
|---|---|
| 機型 | `<MODEL>`（M1 13 吋 2020）／arm64／macOS 27.0 |
| 記憶體 | **8 GB** |
| 磁碟 | 228 GB 中可用 **45 GB** |
| 內建 Python | **3.9.6**（`/usr/bin/python3`；工作機是 3.14.6） |
| homebrew | **未安裝** |
| yt-dlp／ffmpeg／streamlink／MediaMTX | **全部未安裝** |
| `relay.py` 可攜性 | 已複製到 `~/loopcastr/relay.py`，md5 `5219b4b8166798bd962984c180d55295` 兩邊一致；在 **Python 3.9.6 下 `py_compile` 通過** |

**Python 版本不構成阻礙**：`relay.py` 目前語法與 3.9 相容，不需要為了目標機升級 Python。

**【推論】裝機建議（以下來源的 arm64 可用性本輪未驗證）**：目標機沒有 homebrew，走免安裝二進位即可，不必先裝 brew。

## 6. 建議參數（可直接貼）

```
python3 relay.py \
  --playlist playlist.json \
  --watchdog 10 \
  --startup-grace 15 \
  --flow-threshold 12 \
  --url-max-age 1800 \
  --url-expiry-margin 600 \
  --max-restarts 20 \
  --retry-interval 8 \
  --restart-mode auto
```

| 參數 | 舊值 | 新值 | 一句話理由 |
|---|---|---|---|
| `--watchdog` | 3.0 | **10** | 來源片段 5.1 秒，3 秒每 20 秒誤觸發一次 |
| `--flow-threshold` | 5.0 | **12** | `bytesReceived` 每片段才更新，需 ≥2 倍片段長度 |
| `--startup-grace` | 12 | **15** | 容納 YouTube 端建流 |
| `--url-max-age` | 1800 | **1800**（維持） | manifest TTL 6 小時 |
| `--url-expiry-margin` | 300 | **600** | 提前 10 分鐘換手 |
| `--max-restarts` | 6 | **20** | 門檻修正後不會被誤觸發吃光 |

## 7. 明確標為「推論」、尚未實測的部分

1. manifest URL 到期後 googlevideo 是否真的回 403 —— 依 `expire` / `ip` 欄位推導，**未等 6 小時實測**。
2. 公網 IP 變更（PPPoE 重撥）後 URL 失效 —— 同上，無法在測試環境製造。
3. 動態內容（MV、演唱會）的實際位元率 2～3 Mbps —— 依 `itag 95` 名目值，**未實測動態源**。
4. 目標機上的併發承載能力 —— 該機連 ffmpeg 都還沒裝，**完全未測**。
